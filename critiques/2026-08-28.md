## 3. Selector-rot hotspots

No rot yet (one capture, one run — there is no second data point to rot
against). Two things are worth watching as candidate hotspots:

- **The `/help` hydration swallow is the real instability**, not a selector.
  `reviews/2026-08-28.md` read the committed failure artifact: a click landed
  and the URL stayed on `/help` for the full 5s. It is intermittent, and it is
  currently absorbed by `toPass` retries in nine routing tests. That is the
  correct trade, but it means a genuine regression on those routes costs 15s to
  surface instead of 2s, and the absorption is invisible in the report.
- **The two raw selectors are justified, not rot.** `PricingPage`'s
  `.locator('p')` and `.locator('summary')` were empirically defended in review:
  on a collapsed `<details>`, `getByRole('paragraph')` resolves to **0**
  elements, so the role locator would have made `toBeHidden()` vacuously true.
  RULES.md permits this with a comment and the comment is substantive. Leave
  them alone; the failure mode to watch is someone "cleaning them up".

## 4. Page-map staleness

Fresh — `crawled_at` 2026-08-29T02:07Z on both, roughly one hour before the
suite ran. `changed-pages.json` is `[]`, consumed by the Author as designed.
Two defects in the artifacts themselves:

- **`status_code: 307` on both pages, which are really 200.** Drafted this pass

## 5. Reviewer catch-rate

The strongest link in this run. Round 1: **3 `fix` verdicts across 11 rows
(27%)**, and one of them — FAQ order asserted only inside message strings, so
any permutation passed — is exactly the vacuity class the Reviewer exists to
catch; a self-grading Author would have shipped it. Round 2 came back all
`pass`, verified the fix by swapping two items in the live DOM and watching the
assertion fail in 2.0s, and re-probed the failure timing three times rather
than trusting round 1.

Two behaviors worth making permanent:

- **Round 2 re-reviewed the whole batch, not the deltas** — and that is how it
  caught that round 1's *mechanism* was wrong (it claimed `toPass` cannot
  interrupt an in-flight callback; it can — `pollAgainstDeadline` races against
  the deadline) while the verdict stood. A delta-only re-review would have
  carried a false claim forward as fact.
- **The Reviewer escalated rather than expanded scope.** The `SignupPage`
  page-map gap was flagged to the Steward, not fixed by the Author. That is the
  right instinct and it produced draft (b) this pass.

## 6. Process critique of *this* validation run

The run deliberately collapsed the spec §11 gates into one end review
(`docs/plans/2026-08-28-testah-v1.md`, line 11). That was the right call for a
first pass, and it is not free:

- **Criteria were never human-approved before tests were generated from them.**
  This is the gate to restore *first* in production. The four criteria files are
  good, but they encode product decisions a human owns — most sharply
  `card-grid.md` Sc. 3, which deliberately pins the Deep Reports card/sidebar
  inconsistency as expected behavior. That is defensible and stated, and it is
  precisely the kind of judgment that should not have shipped unreviewed.
- **Three drafts encode currently-failing behavior and need a decision, not an
  approval.** They will make the suite red on merge as written:
  `…-guard-help-index-against-layout-shift-regression` (asserts CLS ≤0.1;
  today it is 0.2788, and the draft offers ≤0.28 as a ratchet alternative),
  `…-cover-help-mobile-navigation-drawer` (three a11y assertions the draft
  states "will fail until fixed": Escape-to-close, body scroll lock,
  `aria-expanded` + focus move), and
  `…-cover-anonymous-render-of-the-pricing-page` (a no-console-errors assertion
  that fails today on the site-wide `/favicon.ico` and `/icon-192.png` 404s
  unless an explicit allowlist lands with it). Each is a legitimate
  "pin the fix" ticket **or** a red suite, depending on whether the fix is
  scheduled. The loop has no state for "expected-failing until fixed" —
  `RULES.md` has `@flaky` and `@seed-failure` but nothing for this.
- **CI e2e runs against live staging with no secrets plumbing and no gate.**
  `.github/workflows/tests.yml` runs `pnpm exec playwright test` with no env
  block; `playwright.config.ts` defaults `baseURL` to
  `https://staging.vizaeo.com`. Today the suite is read-only and anonymous, so
  it works — but nothing enforces that, `TESTAH_BASE_URL` is undocumented in
  the workflow, and the first authenticated role will need
  `.auth/<target>/<role>.json` produced by a setup project from secrets that
  have nowhere to come from. `tests/fixtures/` is currently an empty directory.
- **The suite is red on `master` until the seed is deleted.** The first push
  will show a red `e2e` job. That is the plan's own expectation (Task 14
  expects "`e2e` red only on `@seed-failure`"), but it should be a conscious
  choice, not a surprise.
- **Date convention drift, already live in the artifacts.** `agents/scout.md`
  says "`<date>` everywhere means ISO `YYYY-MM-DD`" without a timezone. The
  machine is UTC-5, so the same evening produced `triage/local-2026-08-28.md`
  and `reviews/2026-08-28*.md` (local) alongside ten Scout drafts dated
  **2026-08-29** (UTC). Artifacts cross-reference each other by date; the
  requirements files already link drafts by their `2026-08-29-` filenames while
  citing a `2026-08-28` run.
- **The ticket-draft `source:` vocabulary is too narrow.** `agents/steward.md`
  allows `triage/<run-id>.md` or `page-maps/<target>/<slug>`. Draft (b) this
  pass originates in `reviews/2026-08-28.md`, so it uses a source the format
  does not name.
- **No mobile project exists.** `playwright.config.ts` defines exactly one
  project (`chromium`, Desktop Chrome). The mobile-drawer draft was judged at
  390×844 and cannot be implemented without an architecture-level change.

**Verdict on the seed failure:** honoring `triage/local-2026-08-28.md` — **no
ticket**. The plan (Task 13 Step 6) anticipated a framework-update draft for it;
the triage evidence says otherwise and the triage is right. Filing a
framework-update for a spec whose own header instructs its deletion would put a
fictional defect in the tracker and teach the loop that deliberate scaffolding
is a bug. The triage path is proven by the *document*, not by a ticket.

## Recommendations

**Scout:**
1. When a "Broken / suspect" entry is a product defect rather than a coverage
   gap, say so explicitly in the run summary and hand it to the Steward, rather
   than either dropping it or reshaping it into a test-feature draft. The
   `/help` top-bar dead-end and `/pricing`'s total absence of navigation are
   both stranded right now.
2. Stamp dates in UTC (or state the timezone), so a single loop iteration
   produces one date across all artifacts.
3. On the next pass, re-run the redirect check *by status* as well as by
   `final_url` — and treat a contradiction between the two as an anomaly to
   report, not a page to quarantine.

**Author:**
1. `tests/fixtures/` is empty. Before the first authenticated role lands,
   decide what the auth setup project looks like — `RULES.md` already mandates
   `.auth/<target>/<role>.json` from a `*.setup.ts` project, and nothing
   implements it.
2. A mobile project in `playwright.config.ts` is a prerequisite for the
   mobile-drawer draft. Treat it as the architecture-level change it is.
3. Keep the `toPass` + per-attempt `goto` pattern, but note in the next triage
   whether the `/help` hydration swallow recurs — an intermittent defect being
   silently absorbed by retries is worth a data point per run.
4. When implementing any of the three failing-by-design drafts, tag them so a
   red run is legible at a glance. Ask the human for a tag rather than
   inventing one — `RULES.md` is human-owned.

**Reviewer:**
1. Keep re-reviewing the full batch on repeat rounds. It caught a wrong
   mechanism this run.
2. Keep escalating instead of expanding scope, and keep writing the empirical
   probe into the review — "I swapped items 0 and 1 in the live DOM and it
   failed in 2.0s" is what made the teeth verdict trustworthy.

**Human (Andrew):**
1. **Restore the criteria-approval gate first** when the loop goes
   production — before the ticket gate. It is the one place an agent encodes a
   product decision.
2. **Decide the three failing-by-design drafts** (CLS budget, mobile drawer
   a11y, pricing console errors): schedule the fix and land the strict
   assertion, land the ratchet, or defer. Do not approve them as ordinary
   coverage.
3. **Decide the `SignupPage` question** (draft b): designate `/signup` in
   `targets.yaml`, or add the destination-only carve-out to `RULES.md`. Either
   way `RULES.md`'s "No other exemptions exist" needs an edit — agents cannot
   make it.
4. **Add an "expected-failing" tag to `RULES.md`** if the failing-by-design
   pattern is one you want to keep. Otherwise the rule is "the suite is green",
   and these drafts do not belong in it.
5. **Linear project `testah` does not exist yet** — nothing can be filed. All
   twelve drafts stay `status: draft`.
6. **No git remote is configured**, so CI has never run and the `tests`
   workflow is unproven. Expect `e2e` red on the first push until the seed spec
   is removed; consider removing it in the same push.
7. **Widen the ticket `source:` vocabulary** in `agents/steward.md` to include
   `reviews/<date>.md` (and, when Gauge lands, `load/`).
