## Purpose

Produce two portfolio projects that sell each other:

- **Project 1 — testah**: the AI test-generation pipeline, presented as a
  usable product: a brief "how to use it" story, a consolidated command
  reference, and — the centerpiece — a locally-runnable **UI dashboard**.
- **Project 2 — toolshop-showcase** (separate repo): a Playwright framework
  built to current industry standards against practicesoftwaretesting.com,
  *generated through testah* and curated by Andrew. Its README credits
  testah ("scaffolded by my AI test-generation pipeline; architecture and
  standards mine") and links back.

The two form a **meta-loop**: building #2 with testah stress-tests testah;
every friction point becomes a framework ticket in #1; fixes sync to the
template; #2 pulls them. Each iteration improves both portfolio pieces.

## Project 1 workstream — testah as a product

### 1a. The dashboard (centerpiece)

`scripts/dashboard.py` → `docs/dashboard.html`, one page, self-contained
(inline CSS/JS, no network), same aesthetic as the coverage maps. Sections,
in value order:

1. **Needs you** — the human's queue, computed from artifacts: criteria at
   `approved: false` (with their Judgment calls inline), `scout-observed`
   flags awaiting Steward validation, behavior-change decisions, ticket
   drafts by status/type.
2. **Last run** — pass/fail/flaky counts, failing tests with triage verdicts
   (joined from the latest `triage/*.md`), link to the Playwright HTML
   report and to `reports/last-run.json`.
3. **Coverage** — the per-target coverage maps embedded (iframe/inline) or
   linked, plus headline numbers (features covered / criteria-only / drafts).
4. **Benchmarks** — Core Web Vitals per page over time. Prerequisite:
   Scout currently overwrites `perf.json`; add an append-only
   `perf-history.jsonl` per page (one-line change to `agents/scout.md` +
   the artifact contract) so trends exist.
5. **Test tree** — specs/POMs/fixtures with tags and `implements:` links.
6. **Tickets & critiques** — queue table; latest critique.

Runtime: `uv run python -m scripts.dashboard` regenerates;
`--serve [port]` starts a stdlib `http.server` on the docs dir and prints
the URL; add `"dashboard": "uv run python -m scripts.dashboard --serve"`
to package.json scripts. Agent wiring: Author Mode B and the Steward
regenerate it in their closing commits (same rule as coverage maps).
Tested like the other scripts (pytest on the data-assembly functions).

### 1b. The "sell it" docs

- **README "Use it" brief**: a compact narrative section — clone template →
  `bash setup.sh` → `/scout` → approve criteria → `/author` → green suite →
  `/triage`/`/steward` → dashboard screenshot. Ten minutes to first value.
- **Command reference**: consolidate the setup-menu list + running-the-loop
  commands into one README table (slash commands = LLM skills; scripts +
  playwright = agentless), replacing scattered mentions.
- Dashboard screenshot/GIF embedded in the README (assets/ dir, template-
  synced? → open question 3).

### 1c. Exit criteria for Phase 1

Dashboard generates from real repo state, `--serve` works, README updated,
docs/running-the-loop.md documents the dashboard (same-commit rule), unit
tests green, synced to template.

## Project 2 workstream — toolshop-showcase

### 2a. Bootstrap (this IS testah's first fresh-machine test)

```
git clone --branch template --single-branch <testah> toolshop-showcase
cd toolshop-showcase && bash setup.sh
```
Answer the wizard for real (remote: github private repo; deps; target:
toolshop / https://practicesoftwaretesting.com, first pages: home `/`,
login `/auth/login`; tracker: Linear workspace testah — see open question 2).
**Every wizard friction, unclear prompt, or failure = a framework-update
draft filed back to testah.** This bootstrap is deliberately unassisted-user
role-play.

### 2b. RULES.md — "industry standards edition" (the leverage point)

RULES.md is how Andrew's expertise steers what testah generates. Rewrite it
for the showcase with the current best-practice bar the Author must hit:

- TypeScript strict; ESLint + `eslint-plugin-playwright`.
- Locators: `getByRole` with accessible names first, `data-test` ids second
  (Toolshop ships them), raw CSS/XPath only with a justifying comment.
- POM: composition, locators as readonly fields, **no assertions inside
  POMs** — assertions live in tests; `test.step()` for readable traces.
- Fixtures: typed `test.extend` fixtures for POMs, API client
  (`request` context), seed/cleanup **via API not UI**; auth via setup
  project → `storageState` per role (customer, admin), one Playwright
  project per role consuming it.
- Projects: chromium + firefox + webkit + one mobile viewport; fullyParallel;
  CI sharding with `merge-reports`.
- Flake discipline: retries CI-only, `trace: on-first-retry`, screenshots on
  failure, web-first assertions, zero `waitForTimeout`.
- Test types: e2e ON, **API ON** (Toolshop's documented API), a11y ON
  (`@axe-core/playwright` scan per page class), visual OPTIONAL
  (`toHaveScreenshot` on stable components) — decide per open question 4.
- Tags: `@smoke` `@regression` `@a11y` `@api`; CI stages grep them.
- Env: `.env` layering per environment; no secrets committed (Toolshop's
  demo creds are public but still flow through `.env`/storageState, showing
  the right habit).

### 2c. Loop iterations against Toolshop (the actual generation)

- **Iteration 1 (anonymous)**: `/scout toolshop` (home, category, product
  pages) → Andrew approves criteria → `/author` builds the framework
  skeleton + first specs → agentless run → `/triage` → `/steward`.
- **Iteration 2 (RBAC — first time ever)**: add `roles: [customer, admin]`
  + authed pages (account, admin dashboard) to targets.yaml; Scout uses
  storageState; Author builds the auth setup project + per-role projects.
  Expect testah gaps here; ticket them upstream.
- **Iteration 3 (depth)**: cart/checkout flow, API test suite, a11y specs,
  optional visual. Flake policy proves itself on webkit/mobile.
- Gates: normal testah gates throughout (criteria approval, ticket drafts,
  PR merges) — Andrew is the reviewer of record, which is itself part of
  the showcase story.

### 2d. Polish

README for #2 written as an engineering document: architecture rationale
(why these fixtures, why no assertions in POMs, why API seeding), the
projects/sharding matrix, how to run locally + CI, report artifact links,
the testah credit + link. CI: matrix + shard + `merge-reports` + HTML
report artifact. Tag `v1.0.0`.

## The meta-loop (how the two projects improve each other)

1. Anything testah does badly during #2 → `framework-update` draft **in the
   testah repo's queue** (routing: open question 2).
2. Fix lands on testah master → auto-syncs to template.
3. `toolshop-showcase` pulls framework updates from template (documented
   one-liner: `git remote add upstream <testah> && git fetch upstream
   template && git checkout upstream/template -- <framework paths>`).
4. Repeat until an iteration produces zero upstream tickets — that's the
   "testah is ready" signal the portfolio copy can honestly claim.

## Open questions for refinement

1. **Dashboard scope for v1**: all six sections, or ship 1–3 (needs-you,
   last-run, coverage) first and add benchmarks/tree/tickets in a second
   pass? (Recommend: 1–3 + tickets table first; benchmarks need history to
   be interesting anyway.)
2. **Ticket routing across the two repos**: same Linear workspace (testah)
   with two projects — `testah` for framework tickets, `toolshop-showcase`
   for the demo target's findings? (Recommend yes; needs the per-target
   `bug_destination` field to graduate from "reserved" to implemented, or a
   simpler convention: showcase Steward files testah-framework findings
   into the testah repo's local queue via PR.)
3. **Screenshots in the template-synced README**: embed images (assets/ must
   then sync) or keep the template README image-free and only the private
   master carries visuals? (Recommend: images live in master README only —
   needs a small exception note, or a separate PORTFOLIO.md not synced.)
4. **Visual regression + a11y**: both in the showcase (stronger signal, more
   flake surface on a third-party site) or a11y only? (Recommend a11y ON,
   visual limited to 2–3 stable components with generous maxDiffPixels.)
5. **Recording**: worth producing a 2–3 min screen recording of the loop
   (setup.sh → /scout → approval → green run → dashboard) for the Upwork
   post? (Recommend yes — it's the strongest artifact a private repo can
   offer.)
