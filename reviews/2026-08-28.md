## fix — pricing-faq-accordion.spec.ts:14-28, "renders four questions, all collapsed on load"

Scenario 1 of `requirements/vizaeo/pricing/faq-accordion.md` pins the four
summaries "in this order". This test never checks order. The loop destructures
`index` at L14 but consumes it **only inside assertion message strings** (L18,
L21, L26); every locator resolves by question text via
`pricing.faqItem(entry.question)` / `faqSummary(entry.question)`. All four items
could render in any permutation and this still passes — the `index` variable
makes it read as position-aware on a skim when it is not. The batch already
contains the correct pattern: `help-card-grid.spec.ts:38-42` pins card order with
`help.cards.nth(index)`. Positional addressing of `pricing.faqItems` is what is
missing. I confirmed live that DOM order already matches `PRICING_FAQ`, so the
added assertion will pass as-is.

## fix — help-card-grid.spec.ts:57-62, card "<title>" routes to its article (all nine)

The hydration race is real — I read the committed failure artifact
(`test-results/help-card-grid--…-izaeo-routes-to-its-article-chromium/error-context.md`:
click landed, URL stayed on `/help` for the full 5s). Wrapping the click in
`toPass` is a legitimate answer to it, and teeth are **not** compromised: a
genuinely broken route still fails. The defect is that the `toPass` callback is
not idempotent, which `toPass` requires. The callback assumes it is still on
`/help`, but its own `click()` can leave `/help` — so on any retry that follows a
*wrong* navigation, `help.card(...)` is being resolved against the wrong
document. `playwright.config.ts` sets no `actionTimeout` (default 0 = no
timeout), and `toPass` cannot interrupt an in-flight callback, so the retried
click blocks straight past the 15s `toPass` budget until the 30s test timeout. I
verified the block empirically: on `/help/getting-started`, `main` holds 9 links
and **0** named "Getting Started", so the retried click waits indefinitely.

Net effect when a card's `href` regresses: instead of the clean
`toHaveURL expected /help/getting-started, received /help/<wrong>` at ~2s, the
suite reports a 30s test timeout on `locator.click` for a card it could not find
— pointing the debugger at the grid rather than at the route, which is the actual
defect. The retry needs to re-establish its own precondition (or otherwise bound
the retried action) so the failure surfaces inside the `toPass` budget and names
the URL mismatch.

## fix — pricing-primary-cta.spec.ts:34-39, "following the CTA reaches the signup page"

Same flaw, same reasoning as above: the `toPass` callback at L34-39 clicks
`pricing.primaryCta` and then asserts the URL, but a wrong navigation leaves
`/pricing`, and `page.getByRole('link', { name: 'Get Your Visibility Scoreboard' })`
resolves to nothing on the destination — so the retried click blocks to the 30s
test timeout instead of failing at the 2s URL assertion. Fidelity and teeth are
fine; the retry just needs to be self-contained.

## Notes (non-blocking — no verdict impact)

- **`PricingPage.faqAnswer()` using `.locator('p')` is correct, and the
  justification holds.** I checked it live: on a collapsed item,
  `getByRole('paragraph')` resolves to **0** elements while `.locator('p')`
  resolves to **1** (hidden). Had the role locator been used, the
  `toBeHidden()` at faq-accordion L24-27 would have been vacuously true against
  an empty locator. RULES.md permits a raw selector with a justifying comment;
  this one is substantive and empirically right. Same for `.locator('summary')`
  — `<summary>` has no role mapping.
- **HTTP status assertions are acceptable here.** `expect(response?.status()).toBe(200)`
  reads the browser's own navigation Response inside an e2e flow — it is not an
  "API test" in the RULES.md sense (no separate request context), and a settled
  Response has nothing to retry, so a non-retrying assertion is the only correct
  form. Worth the Author knowing it is *weak on its own*: `page.goto` follows
  redirects and returns the final response, so a `/help` → `/login` regression
  would still report 200. The paired `toHaveURL` is the load-bearing check, and
  it is present in every case — hence teeth ok. The status assertion still
  catches a 404/500, so it earns its place.
- **Pinning the Deep Reports gap is defensible.** `card-grid.md` Scenario 3
  states the inconsistency explicitly and instructs that closing it must turn
  the test red on purpose, so the test is faithful to a criterion a human owns —
  not a test inventing a bug as a feature. It is also double-pinned
  (`toHaveCount(9)` in Scenario 1 plus `card('Deep Reports')` → 0), so adding
  the card fails loudly in two places.
- **`SignupPage` has no page-map** (`page-maps/vizaeo/signup/` does not exist),
  which sits awkwardly with RULES.md "selectors come from the page-map". It uses
  `getByRole` throughout (top of the preference order), the three selectors are
  named by the criterion itself, and the class documents the deviation. Not an
  Author problem to solve — flagging for the Steward: either capture a `/signup`
  page-map or note the carve-out for non-target destination pages.
- `help-anonymous-access.spec.ts:41` navigates to a bare `'/dashboard'` with no
  POM. Acceptable — the test observes only the redirect URL, and a POM for a page
  never inspected would be ceremony.
- `help-anonymous-access.spec.ts:32` (`not.toHaveText('')`) is effectively
  unreachable as a failure, since the preceding `toBeVisible()` already requires
  a non-empty box. Harmless redundancy, not a substitute for a stronger check —
  the criterion asks for nothing more.
